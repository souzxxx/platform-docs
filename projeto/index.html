    Project

    A microservices platform for a store: the user signs up, logs in and checks exchange rates between currencies. Every request comes in through a single entry point (the gateway, behind an Nginx load balancer), which validates the JWT token and forwards the user's identity to the services. It runs with Docker Compose locally and on EKS (AWS Kubernetes), with deployment through GitHub Actions.

    Gateway

    Repository: pna26/gateway-service · Group page: Gateway

    Built with Spring Cloud Gateway on WebFlux, starting from hands-on 2 and 3. The gateway:

    1. routes each path to the right service (/auth/**, /accounts/**, /exchange/**);
    2. authorizes: outside the open routes (sign-up, login, logout), it requires the cookie with the JWT, validates the token against Auth (POST /auth/solve) and forwards the account id in the id-account header;
    3. discards any id-account coming from the client, so no one can impersonate another account;
    4. stores the token validation result in Redis (cache);
    5. exposes GET /health-check with the replica's hostname, which shows load balancing working.

    mvn verify runs 20 tests, also in CI on every push: open routes, token cache (the key is the SHA-256 of the token and the TTL never exceeds exp), authorization filter (no cookie → 401, Auth down → 503, a cache hit does not call Auth) and a test that starts the real gateway against a fake Auth and a fake Account and checks that a forged id-account is discarded.

    CI/CD

    Group page: CI/CD

    Instead of one pipeline per repository, I wrote one reusable workflow in platform (.github/workflows/service.yaml) and each service has only a small ci.yaml that calls it. A fix in the pipeline applies to all of them.

    flowchart LR
    push(["push to main"]) --> build["build and tests<br/>(Maven or pytest)"]
    build --> trivy["Trivy<br/>code and image"]
    trivy --> gate{"fixable CRITICAL<br/>or secret?"}
    gate -->|yes| fail([fail])
    gate -->|no| img["multi-arch image<br/>GHCR + ECR"]
    img --> deploy["deploy to EKS<br/>(kubectl apply + rollout)"]
    • No AWS key on GitHub: the job signs in to AWS through OIDC, assuming an IAM role with only what it needs (ECR and eks:DescribeCluster). Proven in the main runs, with the image published to ECR (evidence).
    • Compatible with repositories that did not have OIDC yet: the reusable workflow inherits the caller's permissions; without id-token: write, the pipeline stays green and publishes to GHCR only.
    • Deployment to EKS turns on by itself when the EKS_CLUSTER variable exists in the organization (the cluster is deleted outside of testing to save money). Proven on 16/11: with the cluster up, the same pipeline published and deployed account, auth and notification without any manual command (kubectl apply + rollout status green, runs).

    The integration workflow in platform brings up the whole platform with compose on every push and PR, runs the smoke test (which requires at least two gateway replicas responding) and OWASP ZAP.
